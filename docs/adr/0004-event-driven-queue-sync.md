# Queue sync is event-driven and never polls

Queue sync saves the queue with `savePlayQueue` on events (song change, queue edit, pause, seek, app backgrounding), debounced, and reads the server's saved queue only on app start, on return to the foreground, and when play is pressed outside the app (notification, widget, Bluetooth) while online. Nothing polls during playback. A live sync would need a timer that keeps the radio awake while music plays from the buffer, and Segue's battery goal rules that out. The cost is that a queue saved by another client is noticed only on the next start, return or play from outside the app, as a *Continue from &lt;device&gt;* offer or an automatic adoption, never mid-session.

Outside the app the banner cannot show. With *Continue automatically* on, play pressed there waits up to two seconds for the server's queue and plays another client's newer queue instead of the local one. With it off, the local queue plays at once and the server is asked meanwhile: a newer queue is offered in a *Continue from &lt;device&gt;* notification, whose **Continue** takes it over and plays it. *Ask in a notification* turns that off, and then the server is not asked. Without the notification permission it is not asked either.

The queue is uploaded as it is, because the queue order is the play order (ADR-0002), so other clients see what is actually playing. When the server advertises the OpenSubsonic `indexBasedQueue` extension, the index-based variants are used instead, because they handle duplicate songs in the queue correctly. Both are sent as form POSTs (OpenSubsonic `formPost`, which Navidrome supports), since a queue of thousands of songs, such as "Shuffle all" of a whole library, is far too long for a URL.
